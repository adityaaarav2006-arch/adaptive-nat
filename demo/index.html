Adaptive NAT Traversal

When two people behind home routers start a video call, the call often ends up going through a slow relay server. Our agent first measures how each router behaves, then picks the cheapest way to connect directly, and only uses the relay when nothing else can work.

      9Honest scope

      Limitations and future work

      What our measurements do not cover yet, and where we would take the project next.

      Limitations

      • Simulator follows RFC 4787 exactly. Real routers can mix behaviours or change them under load.
      • One-machine testbed. Three Linux NAT types in network namespaces, with no real delay or packet loss.
      • TTL = 2 matches the testbed. Real paths have more hops, so the value would need probing.
      • JSON probes instead of binary STUN. The aioice runs do use real STUN.
      • Minimal relay, not a production TURN server such as coturn.
      • Adaptive keepalive not implemented.
      • Block detection assumes aligned blocks. Unaligned blocks would need a range-based estimate.

      Future work

      • Real routers and mobile networks, including carrier-grade NAT on 4G/5G.
      • Automatic TTL: measure the hop count to our own NAT instead of assuming 2.
      • WebRTC integration: use the profile to steer ICE candidate checks in browsers.
